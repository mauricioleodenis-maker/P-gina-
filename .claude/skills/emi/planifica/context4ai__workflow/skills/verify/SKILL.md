# Verify

A unified quality verification skill. Runs typecheck, lint, unit tests, and E2E tests with configurable scope. Filters known runtime noise, persists logs, and performs source-level failure analysis on any failures.

---

## Agent Responsibility Boundaries

The agent's role when running `/verify` is strictly limited to:

1. **Execute** quality checks according to the requested level
2. **Collect** and persist logs
3. **Filter** known runtime noise from results
4. **Analyze** failures at the source level and report findings

The agent MUST NOT:

- Auto-fix any errors or warnings discovered during verification
- Modify source code, configuration, or test files
- Re-run failed checks after making changes
- Suggest or apply patches without explicit user request

If failures are found, the agent reports a structured analysis. The user decides next steps.

---

## Parameter Format and Routing

```
/verify [level] [scope]
```

| Invocation | Level | What Runs |
|---|---|---|
| `/verify fast` | fast | typecheck + lint + unit tests (no E2E) |
| `/verify` | standard | fast + default E2E layer |
| `/verify full` | full | fast + all E2E layers |
| `/verify e2e [scope]` | e2e-only | E2E tests only (skips typecheck/lint/unit) |

### E2E Sub-routing

When E2E tests are included, the `[scope]` parameter controls which E2E layer(s) run:

| Scope | Meaning |
|---|---|
| *(omitted)* | Default E2E layer only |
| `all` | All E2E layers |
| `<layer-name>` | Specific named layer |
| `<glob-pattern>` | Pattern-matched layers (e.g. `stable/*`) |

### Route Decision Flow

```
User invokes /verify [args]
│
├─ args = "fast"
│   └─ Phase A only (typecheck + lint + unit tests)
│
├─ args = "" (empty / standard)
│   └─ Phase A → Phase B (default E2E layer)
│
├─ args = "full"
│   └─ Phase A → Phase B (all E2E layers)
│
├─ args = "e2e [scope]"
│   └─ Phase B only (E2E with given scope)
│
└─ args = unrecognized
    └─ Report error: unknown parameter
```

## Usage Examples

### Incremental Testing Strategy

During iterative development, use verify levels incrementally:

```
# 1. After changing types or interfaces — quick static check
/verify fast

# 2. After implementing a feature — standard verification
/verify

# 3. Before merging or releasing — full verification
/verify full

# 4. Re-run only E2E after fixing a test-specific issue
/verify e2e stable
```

## Three-Level Verify System

| Level | Includes | Typical Use Case |
|---|---|---|
| **fast** | typecheck, lint, unit tests | Quick feedback during active development |
| **standard** | fast + default E2E | Feature completion check |
| **full** | fast + all E2E layers | Pre-merge / pre-release gate |

### Agent Role vs Verify Level

| Agent Role | Recommended Verify Level |
|---|---|
| Implementing a single task from Plan | `fast` after each change, `standard` on completion |
| Implementing a full feature | `standard` iteratively, `full` on completion |
| Reviewing / auditing | `full` |
| Debugging a specific E2E failure | `e2e <specific-layer>` |

## Cross-Package Breaking Change Typecheck Exemption

When a Plan explicitly calls for cross-package breaking changes (e.g., updating a shared interface that multiple packages consume), typecheck errors in **downstream consumer packages** that have not yet been updated are **expected**. In this case:

- The agent MUST still run typecheck and report all errors
- The agent MUST note which errors are attributable to the planned breaking change
- These errors are **exempt from blocking** the verify result — they should be flagged as "expected cross-package breakage per Plan"
- Errors in the **source package** (the one making the breaking change) are NOT exempt

---

## E2E Todo Exclusion Rules

Test files that contain ONLY `test.todo(...)` placeholders (skeleton tests generated by `/make-test-plan`) are **excluded** from E2E execution. They are not yet implemented and would produce false failures.

- A file with at least one `test(...)` (non-todo) IS included
- A file with only `test.todo(...)` IS excluded
- The agent should report excluded skeleton files in the output summary

---

## E2E Verification Type Relationship

E2E tests are categorized by verification type (as defined by `/make-test-plan`):

| Type | Meaning | Relationship to `/verify` |
|---|---|---|
| **AUTO** | Fully automatable, runs in CI | Included in `/verify` E2E execution |
| **AGENT** | Requires agent judgment (visual, semantic) | Included in `/verify` but may need agent-assisted assertion |
| **HUMAN** | Requires human interaction or subjective evaluation | Excluded from `/verify` — reported as "requires manual verification" |

---

## Multi-Agent Parallel Error Attribution

When multiple agents work in parallel on different Plan tasks and `/verify` reveals failures, follow these three steps for error attribution:

1. **Isolate**: Identify which test files / checks failed
2. **Trace**: Map each failure to the source file(s) that caused it, using stack traces and error messages
3. **Attribute**: Match source files to the Plan task (and thus the agent) responsible for that area of code

Report attribution as a table: `| Failure | Source File | Plan Task | Likely Owner |`

---

## Log Management

All verify runs persist logs for later analysis:

- Logs are written to the configured log directory (see project config below)
- Each run creates a timestamped log file: `verify-<level>-<YYYYMMDD-HHmmss>.log`
- Logs include: full command output, filtered noise annotations, and the final summary
- Old logs are NOT automatically cleaned up — the user manages retention

### Command Mappings

Map each verify phase to your project's actual commands:

| Phase | Command Placeholder | Example |
|---|---|---|
| Typecheck | `<typecheck-command>` | `bun run typecheck` or `npx tsc --noEmit` |
| Lint | `<lint-command>` | `bun run lint` or `npx eslint .` |
| Unit Tests | `<unit-test-command>` | `bun test` or `npx vitest run` |
| E2E Tests | `<e2e-command> [layer]` | `bun test:e2e --layer <layer>` |

### E2E Layer Definitions

Define which layers exist and which is the default:

```
layers:
  - name: stable        # default layer
    path: e2e/stable/
    default: true
  - name: native
    path: e2e/native/
  - name: integration
    path: e2e/integration/
```

### Log Directory

```
log_dir: .verify-logs/
```

### Known Runtime Noise Filtering

Some runtime environments produce spurious output or exit codes that do not indicate real test failures. Configure patterns to filter:

| Pattern | Description | Action |
|---|---|---|
| Bun NAPI crash (exit code 133) | Bun runtime occasionally crashes with SIGBUS on NAPI modules after tests complete. Exit code 133 with no assertion failures. | Filter: treat as pass if all assertions passed before the crash |
| `[Native module warning]` | Non-fatal native module compatibility warnings | Strip from output |

**Noise filtering rules:**
- Only filter patterns listed here — never silently discard unknown errors
- When a noise pattern is filtered, annotate the log: `[FILTERED: <pattern-name>]`
- If exit code is non-zero but all assertions passed AND the exit code matches a known noise pattern, report as PASS with a note

### PATH Environment Troubleshooting

If commands fail with "not found" errors:
1. Check that the runtime (e.g., `bun`, `node`) is on PATH
2. Check that `node_modules/.bin` is accessible
3. Try running with full path: `./node_modules/.bin/<tool>`
4. Ensure any required environment variables are set before running verify

## Procedures

### Step 0 — Parameter Validation

1. Parse the invocation arguments
2. Validate that the level is one of: `fast`, (empty for standard), `full`, `e2e`
3. If `e2e`, validate the scope parameter (if provided)
4. If invalid parameters, report the error and show the usage table above
5. Confirm the route before proceeding

### Phase A — Static Checks + Unit Tests

Runs for levels: `fast`, `standard`, `full`

1. **Typecheck**: Run the configured typecheck command
   - Capture full output and exit code
   - If cross-package breaking change exemption applies (see above), annotate exempt errors
2. **Lint**: Run the configured lint command
   - Capture full output and exit code
3. **Unit Tests**: Run the configured unit test command
   - Capture full output and exit code
   - Record pass/fail/skip counts

If any Phase A check fails (non-exempt), stop and proceed to Phase C (report). Do NOT continue to Phase B.

### Phase B — E2E Tests

Runs for levels: `standard`, `full`, `e2e`

#### B.1 — Parse Scope

- Determine which E2E layers to run based on level and scope parameter
- Exclude files containing only `test.todo(...)` placeholders
- Report the resolved layer list before executing

#### B.2 — Execute and Log

- Run E2E tests for each resolved layer sequentially
- Stream output to both terminal and log file
- Record start/end timestamps for each layer

#### B.3 — Parse Results and Filter Noise

- Parse test runner output for pass/fail/skip/todo counts
- Apply known runtime noise filters (see project config)
- Annotate filtered items in the log

#### B.4 — Failure Analysis

For each failed test:

1. Extract the failing test name and assertion message
2. Locate the test file and line number
3. Read the relevant source code around the failure point
4. Identify the likely root cause (assertion mismatch, timeout, missing setup, etc.)
5. If applicable, perform multi-agent error attribution (see above)

### Phase C — Output Report

Generate a structured report based on the outcome:

#### Format: PASS

```
## Verify Result: PASS

Level: <level>
Duration: <total-time>

### Phase A — Static Checks + Unit Tests
- Typecheck: PASS
- Lint: PASS
- Unit Tests: <pass-count> passed, <skip-count> skipped

### Phase B — E2E Tests
- Layers: <layer-list>
- Results: <pass-count> passed, <skip-count> skipped, <todo-count> todo
- Excluded skeletons: <count> files (test.todo only)

[Filtered noise: <count> items — see log for details]

Log: <log-file-path>
```

#### Format: Phase A Failure

```
## Verify Result: FAIL (Phase A)

Level: <level>
Duration: <total-time>

| Check | Status | Error Count |
|---|---|---|
| Typecheck | FAIL | <count> errors |

### Failure Analysis

1. `<file>:<line>` — <error-message>
   - Root cause: <analysis>
   - Source context: <relevant code snippet>

```
